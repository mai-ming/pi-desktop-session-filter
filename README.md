# 会话来源过滤（PI-Desktop 插件）

PI-Desktop 的侧边栏把一个项目下所有来源的会话放在同一个列表里：PI-Desktop 自己的会话、原生 Pi 会话、远程主机会话。原生 Pi 会话在标题前带一个 `Pi` 标记。

这个插件让你**勾选想看到哪几类会话**，没勾的就不显示。默认只勾「PI-Desktop 原生会话」，也就是把带 `Pi` 标记的原生 Pi 会话藏起来。每个项目标题栏上有一个漏斗按钮，点开就是过滤菜单。

## 安装

1. PI-Desktop → 扩展页 → **加载本地插件** → 选择本文件夹
2. 插件会申请两个权限：
   - `renderer.extension`（高风险）：渲染模块要跑在主窗口里、往主窗口注入样式和那个漏斗按钮
   - `background.service`（中风险）：一个常驻服务，本身不干活，只用来让宿主在启动时把这个插件通知给渲染进程。原因见下面「怎么工作」
3. 侧边栏立刻变化，不需要重启

以目录形式加载的插件会常驻：文件夹还在，重启 PI-Desktop 后插件仍然生效。

> 改动 `manifest.json` 里的 `permissions` 之后，热重载会被拒绝（宿主不允许热重载自动提权），需要在扩展页里手动重载一次并确认新权限。

## 过滤菜单

漏斗按钮平时不显示，鼠标移到项目标题行上才出现——和宿主自己的「⋯」「＋」两个按钮一样。点开是多选清单，用两条横线分成三组：
按钮在过滤开启时会留一点淡淡的强调色，鼠标移上去才变实——完全隐藏的话，你会看不出"会话变少了"是过滤造成的。

```
过滤会话
──────────────────
✓ 全部显示
──────────────────
  PI-Desktop 原生会话
  Pi 会话
──────────────────
  最新
  近 7 天
  近 14 天
  更早
```

规则只有一条：**勾上什么就显示什么，都没勾就等于「全部显示」。**

| 勾选项 | 覆盖的会话 |
| --- | --- |
| 全部显示 | 什么都不藏（等于没开过滤） |
| PI-Desktop 原生会话 | id 是 uuid 的本地会话 |
| Pi 会话 | id 以 `native-pi:` 开头、带 `Pi` 标记的会话 |
| 最新 | 宿主侧边栏里今天与昨天那两段 |
| 近 7 天 / 近 14 天 / 更早 | 宿主侧边栏里对应的那一段 |

多选之间是**并集**：同时勾「Pi 会话」和「近 7 天」，就是"Pi 会话全部 + 最近 7 天的其他会话"。再点一下取消勾选；把最后一个勾去掉，会自动勾回「全部显示」。勾选变化立刻生效，菜单不关。

过滤是全局的，所有项目共用一套勾选，和 PiDeck 的「过滤历史记录」一致。漏斗按钮在过滤开启时保持高亮，鼠标悬停能看到当前勾了哪几项。

过滤只在显示层生效：会话、消息、文件都没有被改动或删除。

## 设置

扩展页里这个插件有四项设置，改完约 2.5 秒内生效，不用重载插件。

| 设置 | 默认 | 作用 |
| --- | --- | --- |
| 显示哪些会话 | `desktop` | 菜单里那些勾选的另一种写法：逗号分隔的 `desktop` / `pi` / `newest` / `week` / `fortnight` / `older`，留空表示全部显示 |
| 屏蔽远程主机会话 | 关 | 隐藏 id 以 `remote:` 开头的会话。远程会话不在菜单的分类里，默认只在「全部显示」或者勾了时间分类时出现，这个开关是单独的一道闸 |
| 隐藏空的时间分组标题 | 开 | 某个时间分组（今天 / 近 7 天 …）下的会话被全部藏掉后，把标题一起藏掉 |
| 额外屏蔽的会话 id 前缀 | 空 | 逗号分隔，命中任一前缀的会话**总是**被隐藏，优先级高于菜单勾选 |

命令面板里还有一条 **切换 Pi（原生）会话屏蔽**，在「只勾 PI-Desktop 原生会话」和「全部显示」之间切换。

## 怎么工作

侧边栏的每一行是 `div.thread-item[data-sidebar-session-row=<会话 id>]`，这个 id 就是会话 id，来源写在 id 前缀上：

| 来源 | id 形态 |
| --- | --- |
| PI-Desktop 自己 | uuid |
| 原生 Pi | `native-pi:…` |
| 远程主机 | `remote:…` |

时间分组不需要猜：宿主自己的分组标题（今天没有标题）就写在 DOM 里，标题下面的行属于哪一段一目了然。插件内置了宿主 9 种语言的这几条文案（`en / zh-CN / zh-TW / de / es / fr / ko / pt-BR / tr`），所以时间过滤不受界面语言影响。

渲染模块做的事：

- 给要藏的行打上 `data-pi-session-filter="hidden"`，再靠一条 CSS 规则把它 `display: none`。只改显示，不碰数据。
- 往每个项目标题按钮后面插一个漏斗按钮，菜单本身用宿主自己的弹层类名（`sidebar-popover` / `sidebar-sort-menu` / `sidebar-floating-menu` / `sidebar-popover-divider`），所以它自动跟随你的主题和明暗。
- 样式不走宿主的 `pi.ui.injectStyle`，而是自己往 `document.head` 挂一个 `<style>`。原因是宿主的 `injectStyle` 会把每一条规则包进 `@scope ([data-pi-plugin="<插件id>"])`，作用域被限制在插件自己的 DOM 子树里，对侧边栏无效（这个坑我踩过：行被正确打了标记，但视觉上从来没消失过）。
- 一个 `MutationObserver` 盯着 DOM，新建会话、切换项目、改设置都会重扫一遍。
- 配置每 2.5 秒从插件进程拉一次，所以改设置不用重载插件。
- 卸载时，标记属性、按钮、菜单、注入的样式、观察器和定时器全部撤掉。

**为什么要那个常驻服务：** PI-Desktop 启动时恢复插件的循环没有给渲染进程发 `pluginChanged` 事件，而渲染进程只在这个事件（或它开机时那次列表拉取，那时插件还没加载完）之后才知道某个插件带渲染模块。结果是：装好之后立刻可用，**一重启就静默失效**。声明一个常驻服务会让宿主在加载插件时把状态变化广播出去，渲染模块才被拉进来。`pi-desktop-xdpool` 靠的是同一套机制。服务本身不执行任何逻辑。

宿主没有提供"会话列表过滤器"这种 API，也没有侧边栏插槽，所以这里走的是 `renderer.extension` 加 DOM 这条路。

## 已知边界

- 「加载更多（N 条）…」的计数不会跟着变。那个数字由宿主自己算，藏掉的行不从计数里扣。如果一个项目当前展开的 10 条恰好全被藏掉，你会看到空列表加一个加载更多按钮；点一下加载下一批。
- 置顶会话和「临时对话」里的会话不在时间分组里，所以时间勾选管不到它们，只由来源勾选决定。它们属于哪一类就跟着哪一类走。
- 命令面板里的会话搜索结果不受影响。那是另一套 DOM，被藏掉的会话在搜索里仍然找得到。
- 漏斗按钮和菜单是插进宿主 React 树外面的 DOM 节点。宿主重渲染时插件会补回来，但宿主大改侧边栏结构就可能失效——失效的表现是按钮不见或菜单点了没反应，不会损坏数据。
- 依赖宿主的 id 前缀约定。如果哪天 PI-Desktop 换了命名方式，来源过滤会失效；`额外屏蔽的会话 id 前缀` 可以手动补上。

## 开发

```bash
npm install
npm test
```

`tools/verify.mjs` 加载真正的 `renderer/index.mjs` 和 `main.js`，把前者放进 jsdom，DOM 结构照抄自 PI-Desktop 0.20.1 的侧边栏（`tools/fixture.mjs` 里写了出处）。跑一遍：manifest 白名单和实际调用是否对齐、`getConfig` / `setFilters` 的回答、切换命令、单键与多键（并集）的判定、时间分组识别（含多语言）、漏斗按钮的注入位置与图标画法、菜单的三组横线与勾选/取消/自动回到「全部显示」、加载后新增的行、卸载后还原，以及**被藏的行在计算样式上真的等于 `display: none`**。123 项断言。

`package.json` 只服务于这个测试，故意不写 `"type"` 字段：`main.js` 必须保持 CommonJS，宿主是用 `require()` 加载它的。

## 打包与发布

```bash
# 在 PI-Desktop 里用 PluginPack（需要一个打开的工作区），产物落在 dist/
node tools/check-piplug.cjs dist/local.pi-session-filter-0.3.0.piplug
Get-FileHash dist/local.pi-session-filter-0.3.0.piplug -Algorithm SHA256
```

`tools/check-piplug.cjs` 干两件事：确认 zip 里每条都是 store（不压缩）——上游只接受这种；确认 `manifest.json` 在包根。发布前跑一次比事后被安装器拒掉省事，摘要也从这里出。

插件中心是「发布者自己的仓库 + 中心重托管」的模型，默认模式 `publisher-release`：把 `.piplug` 挂到自己仓库的 release 上，中心校验字节和 manifest 后再分发。所以发一版就三步：

1. 升 `manifest.json` 的版本，提交，打 tag `v<version>`；
2. 建 release，附上 `dist/<id>-<version>.piplug`；
3. 在插件中心提交：`pluginId`、`repository`、`path: "."`、`ref: refs/tags/v<version>`、`channel: stable`、`version`，以及 `artifact: { mode: "publisher-release", assetUrl: <release 里的文件地址>, sha256: <上一步的摘要> }`。
